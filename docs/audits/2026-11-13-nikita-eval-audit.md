## A1. Факт-чек по подстрокам пропускает противоположный смысл

Приоритет: высокий. Зона: `eval/runner.py`, строки 125–134.

Для большинства типов ответов проверяется только наличие строк из поля `facts`.
Смысл утверждения, отрицание и подтверждающий источник при этом не проверяются.

Конкретные слабые ожидания:

- Q16: факт `включ`. Фраза «Стоимость упаковки и доставки не включена» содержит этот фрагмент слова, хотя подготовленный п. 2.1 договора П-17/2024 говорит о включении расходов.
- Q18: факт `рабочих дней`. Количество дней не закреплено; в подготовленном п. 3.2 Регламента 2025 указано 3 рабочих дня.
- Q12: факт `распространяются`. Добавление отрицания не устраняет совпадение подстроки.

Предлагается:

1. Описать полные ожидаемые утверждения, условия и источники.
2. Добавить отрицательные примеры: отрицание верного утверждения, неверное число с правильной единицей, неверный источник.
3. Отдельно разрешить смысловые перефразирования; простое расширение списка буквальных строк не решает проблему.

Источник: [проверка фактов](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/eval/runner.py#L125).

## A2. real_eval теряет связь числа с единицей и источником

Приоритет: высокий. Зона: `eval/real_eval.py`, строки 81–101.

Числа и единицы извлекаются в отдельные множества. Проверка `units_of` сохраняет единицу, но не пару «число + единица».

Искусственный пример для будущего регрессионного теста:

- Эталон: «Приёмка — 5 рабочих дней, оплата — 30 календарных дней».
- Ошибка: «Приёмка — 5 календарных дней, оплата — 30 рабочих дней».

Наборы чисел и единиц одинаковы, хотя сроки перепутаны.
Кроме того, числовая проверка ищет недостающие числа эталона и сама по себе не штрафует дополнительные выдуманные значения.
Ссылки сравниваются по номерам `п. X`, без проверки документа, к которому относится пункт.

Предлагается:

- Сопоставлять связанные факты: действие, значение, единица, условие, документ и положение.
- Проверять неподтверждённые дополнения отдельно от полноты ответа.
- Добавить сценарии перестановки сроков и ссылки на тот же номер пункта другого документа.
- Считать текущий score диагностической метрикой, а не подтверждением юридической корректности или эквивалентом оценки организаторов.

Источник: [расчёт score](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/eval/real_eval.py#L81).

## A3. fact_coverage может засчитать обрезанный факт

Приоритет: высокий. Зоны: `eval/fact_coverage.py`, строки 199–207 и 255–264; `pipeline.py`, строки 72–79.

Факт ищется в полном тексте чанка. Затем попадание факта в evidence определяется по идентификатору чанка.
Однако модели передаётся только начало текста, ограниченное `per_fragment`.
Если нужный факт находится после места обрезки, идентификатор будет учтён, хотя сам факт не попадёт в контекст.

Предлагается искать подтверждение в реально отправленном тексте и сохранять привязку факта к документу.

Сценарии для будущих тестов:

- Факт расположен до границы обрезки: покрытие положительное.
- Факт находится только после границы: покрытие отрицательное.
- Чанк целиком не вошёл в общий бюджет: покрытие отрицательное.
- Подтверждение находится в переданной temporal-заметке: учитывать именно её фактический текст.

Источники: [подсчёт покрытия](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/eval/fact_coverage.py#L199), [сборка контекста](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/pipeline.py#L72).

## A4. Содержательные тесты могут быть пропущены без исходной базы

Приоритет: высокий для приёмки. Зона: `tests/test_v2.py`, строки 25–40.

17 из 34 тестов этого файла используют fixture `real_ctx`.
Она требует `data/knowledge-base.zip`; при отсутствии архива вызывается `pytest.skip`.
Архив в проверенном дереве репозитория отсутствует.
Готовый индекс из `index/` эту зависимость в fixture не заменяет.

Поэтому успешное завершение pytest само по себе не доказывает выполнение этих сценариев.
Это вывод о поведении fixture, а не результат запуска тестов.

Предлагается:

- В отчётах показывать выполненные и пропущенные проверки отдельно.
- Определить обязательные для сдачи сценарии, пропуск которых не считается успешной приёмкой.
- Согласовать, какие проверки требуют исходного архива, а какие могут использовать подготовленный индекс или небольшую тестовую базу.

Источник: [условие skip](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/tests/test_v2.py#L25).

## A5. Эталоны нужно уточнить до использования для приёмки

Приоритет: средний; это основная задача Никиты по данным.

В 13 записях по одному факту, в четырёх по два, в одной нет фактов.
Ни одна запись не достигает формального требования личного задания «не менее трёх фактов».
Для отказов нужно согласовать отдельный состав ожиданий, не дополняя записи искусственными фактами.

Точечные замечания:

- Q5: пороги 10 и 15 млн записаны без связи каждого значения с периодом действия редакции.
- Q14: ожидается вся `ч. 1` статьи 59; текущая retrieval-проверка по префиксу может засчитать другой абзац этой части вместо положения о сезонных работах.
- Q16: вместо законченного утверждения записан фрагмент слова `включ`.
- Q18: отсутствует ожидаемое число 3.
- Для false_premise, partial и not_established в `runner.py facts` нет отдельных содержательных условий приёмки.

Предлагается для каждой записи указать:

1. Полное ожидаемое утверждение или допустимую границу ответа.
2. Условия применения: дату, редакцию, событие, договор, контрагента.
3. Документ и подтверждающее положение/фрагмент.
4. Допустимые смысловые варианты ответа.
5. Противоположные или неподтверждённые утверждения, которые должны проваливать проверку.

Окончательно сверять записи следует с исходными вопросами, demo_output и TXT.

Источник: [18 записей gold](https://github.com/v1ewzz/psb-legal-assistant/blob/da0955a5410914c6d806d72cb3adc7478e44bf93/eval/demo_gold.jsonl).
