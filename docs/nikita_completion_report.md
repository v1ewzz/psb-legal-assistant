- `runner.py validate` проверяет файлы, точные демовопросы/ответы, наборы ID,
  52 цитаты с номерами строк и контрольный расчёт пени. Итог PASS относится к данным.
- 31 unittest на стандартной библиотеке проверяет позитивные и негативные варианты,
  пары единиц, числовые подстроки, CSV, границы бюджета, source restriction,
  отсутствие чтения .env/импорта ядра при импорте функции real_eval.
- Оба примера каждой из 12 ловушек приняты/отклонены объявленными правилами.
  Это проверка правил на контрольных примерах, а не 12 успешных ответов модели.
- В исторической диагностике хранятся SHA-256 входов, набора правил и файлов оценивания.
  Историческое имя `head` не означает текущий HEAD; версия генератора этих ответов
  не подтверждена независимо.
- Проверен ZIP: 12 файлов в корне, 214873 байта, нет отсутствующих локальных импортов;
  все Python-файлы в архиве синтаксически разобраны. API/исполнение не запускались.
- Проверенная PDF: 12 страниц, размер как у исходной 960×540, все страницы визуально

## Исправления eval

1. Локальный runner реализован вместо заглушки, без импорта ядра и сети.
2. В real_eval оценка вынесена в чистый модуль: единицы связаны с числами,
   дополнительные числа видимы как review, лишний отказ учитывается симметрично.
3. ID присутствующего чанка больше не используется как доказательство наличия
   факта после обрезки: проверяется сохранённый текст.
4. Для одинакового числа в разных единицах сохраняются обе пары фактов.
5. CSV с дубликатами/пустыми ID, пустыми ответами или лишними столбцами отклоняется.
6. Эталонные правила учитывают отрицания и формы вроде «5 (пяти) рабочих дней»;
   сумма 450 000 не засчитывается внутри 1 450 000.

Ограничения: regex-условия не доказывают смысловую правильность и могут требовать
ручного решения при перефразировании. Дополнительное число не автоматически выдумка.
Ссылки нужно проверять в связке с утверждением и конкретным документом.
Legacy retrieval-adapter fact_coverage относится к v2, не к lean; для него явно
выводится BLOCKED, а не ложный успех. Полноценная метрика recall lean не получена.

## Замечания владельцам ядра и UI

Эти файлы не исправлялись в рамках разрешённого объёма.

1. `webapp.answer_rich` ожидает, что pipeline заполнит `ctx['collect']`; выбранный
   lean-pipeline его не заполняет. По статическому пути возможны пустые sources,
   статус по умолчанию и неполный trace, несмотря на ответ. Нужен реальный E2E.
2. Lean `docs.json` не содержит signed/applies_from ДС, valid_from/valid_to редакций
   и даты начала требования К-12. Тексты есть, но нельзя заявлять готовый кодовый
   выбор редакции/таймлайн по этим отсутствующим полям.
3. Технические пути «блок N» не являются точными юридическими реквизитами.
4. В другом main есть отдельный webapp с эвристическими confidence и признаками
   успешной проверки, не привязанными к результату verify; переносить их в демонстрацию
   как доказанную вероятность правильности нельзя.
5. Докер-сборка устанавливает зависимости; она не запускалась. Web-зависимости
   исходного requirements не все pinned. Версии рантайма сверить с разрешённым набором.

## Передача и финальная приёмка

- Предложение: PR в lean-v1, поскольку именно от неё сделаны изменения. Если команда
  выбирает main, перенос должен быть отдельным согласованным действием, без force/rebase.
- Для завершения нужны: финальный commit команды, отсутствующая спецификация либо
  согласование нашего альтернативного реестра/категорий, результаты API и платформы,
  подготовленное окружение для полного прогона и UI-приёмки.
- Ограничения пользователя соблюдены: установки и удаления не выполнялись,
  никаких новых ответов LLM/baseline/judge не генерировалось, main не изменялся.

Не все задачи исходного DoD можно объявить завершёнными: API, полноценная приёмка
ассистента, исходные списки спецификации и финальная сдача остаются открытыми.
